# ETSI GS QKD 020 v0.1.0 - Reference Implementation

## Description

This project provides a reference implementation to the ETSI GS QKD 020 v0.6.2 standard.

## Installation

### Reference OS

```text
Ubuntu 22.04.1 LTS
```

This implementation has been developed and tested on Ubuntu 22.04.1 LTS.
While no OS specific components are present in this implementation, no
guarantees are made that it works on other OSs.
If you encounter issues deploying this implementation on another OS, reach out
and we will try our best to make it work on your setup.

### Required OS packages

The server requires the following packages to be installed:

- build-essential
- curl
- moreutils
- pkg-config

On Ubuntu, these can be installed using:

```bash
sudo apt install build-essential curl moreutils pkg-config
```

### Rust

The implementation has been developed in Rust and requires the rust toolchain to be installed.
This is typically done using an installation script downloaded with curl.

The installation script can then be downloaded and executed using the command:

```bash
curl --proto '=https' --tlsv1.3 -sSf https://sh.rustup.rs | sh -s -- --default-toolchain=1.93.0 -y
```

Follow the on-screen instructions to install rust.

### Docker

The repository makes use of docker to build the reference implementation image.
Kindly install docker by following the [official documentation](https://docs.docker.com/engine/install/ubuntu/).

To build the image, run `make build_image`.

## Environment setup

Set up your environment by executing the following:

```bash
make setup
```

This will create the necessary [certificates](#certificates).

## ETSI QKD 020 Standard

The ETSI QKD 020 standard requires that mutual TLS (mTLS) authentication is
performed.
This requires both the server and the client to authenticate each other.
Most commonly, only the server's certificate is authenticated by the client,
with the server doing no such authentication.
Due to the sensitivity of the application, mTLS is required.

### Secure Application Entity (SAE)

The SAE refers to the client, because it is the entity that will be
issuing the requests.

### Key Management Entity (KME)

The KME is the application that this server aims to emulate.
It will be referred to as the server.

## Certificates

A root CA will be generated and used to sign both the SAE (client) and KME
(server) certificates.
This is to emulate a certificate that is signed by a trusted Certificate
Authority (CA).

### Generate a self-signed certificate

The generation of a certificate involves the

- Generation of a private key,
- Generation of a certificate signing request, and
- Signing of the certificate.

The generation of a private key and self-signed certificate can be done using a
single command.
The `nodes` option is set such that the private key is not passphrase protected.

```bash
openssl req -x509           \
    -newkey rsa:4096        \
    -days 3650              \
    -nodes                  \
    -keyout test.key        \
    -out test.crt           \
    -subj "/CN=test_123456" \
    -addext "subjectAltName=IP:127.0.0.1"
```

### Certificate generation

All the below commands are part of the included `makefile` in the `certs`
directory.
Certificates can be generated by issuing the command:

```bash
make certs
```

#### Root CA

Generate a password protected root certificate.

```bash
openssl req -x509                                            \
    -newkey rsa:4096                                         \
    -days 365                                                \
    -subj "/C=MT/CN=www.merqury.eu/O=Merqury\ Cybersecurity" \
    -keyout root.key                                         \
    -out root.crt
```

#### KME Certificate

Generate the KME private key and a Certificate Signing Request (CSR).

```bash
openssl req                                          \
    -newkey rsa:4096                                 \
    -nodes                                           \
    -days 365                                        \
    -subj "/C=MT/O=Key Management Ltd/CN=kme_123456" \
    -keyout kme.key                                  \
    -out kme.csr
```

Create an extensions file to specify the alternative names:

```bash
echo "subjectAltName = IP:127.0.0.1" >> kme.ext
```

Sign the certificate using the root CA's key:

```bash
openssl x509 -req    \
    -in kme.csr      \
    -CA root.crt     \
    -CAkey root.key  \
    -set_serial 01   \
    -days 365        \
    -extfile kme.ext \
    -out kme.crt
```

#### SAE Certificate

Generate the sae private key and a Certificate Signing Request (CSR).

```bash
openssl req                                              \
    -newkey rsa:4096                                     \
    -nodes                                               \
    -days 365                                            \
    -subj "/C=MT/O=Secure Application Ltd/CN=sae_123456" \
    -keyout sae.key                                      \
    -out sae.csr
```

Create an extensions file to specify the alternative names

```bash
echo "subjectAltName = IP:127.0.0.1" >> sae.ext
```

Sign the certificate using the root CA's key

```bash
openssl x509 -req    \
    -in sae.csr      \
    -CA root.crt     \
    -CAkey root.key  \
    -set_serial 01   \
    -days 365        \
    -extfile sae.ext \
    -out sae.crt
```

### Utilities

To view the private key contents:

```bash
openssl pkey -in test.key -text -noout
```

To extract the public key from the private key:

```bash
openssl pkey -in test.key -pubout -out server-public.key
```

To view the Certificate Signing Request (CSR) contents:

```bash
openssl req -text -in test.csr -noout
```

To examine the certificate:

```bash
openssl x509 -text -in test.crt -noout
```

# Environment variables

| Variable name                                    | Description                           |
|------------------------------------------------- |---------------------------------------|
| ETSI_020_REF_IMPL_ROOT_CERT                      | The root certificate used by the server.|
| ETSI_020_REF_IMPL_PRIVATE_KEY                    | The servers private key.|
| ETSI_020_REF_IMPL_PUBLIC_CERT                    | The servers public certificate.|
| ETSI_020_REF_IMPL_CLIENT_ROOT_CERT               | The root certificate used during ACK requests.|
| ETSI_020_REF_IMPL_CLIENT_PRIVATE_KEY             | The ACK clients private key used during ACK requests.|
| ETSI_020_REF_IMPL_CLIENT_PUBLIC_CERT             | The ACK clients public certificate used during ACK requests.|
| ETSI_020_REF_IMPL_LOG_LEVEL                      | Maximum log level to print to the terminal.|
| ETSI_020_REF_IMPL_PORT_NUM                       | Which port number to listen on for API requests.|
| ETSI_020_REF_IMPL_IP_ADDR                        | Which IP address to bind to.|
| ETSI_020_REF_IMPL_ACK_CALLBACK_DELAY             | How long to wait before the `ext_keys` endpoint calls the `ack` callback URL in the request.|
| ETSI_020_REF_IMPL_SEND_EXT_KEYS_ENABLE           | Whether to enable the ext_key dispatching subsystem of the ref impl server.|
| ETSI_020_REF_IMPL_SEND_EXT_KEYS_INTERVAL_SECONDS | The duration in between `ext_key` requests.|
| ETSI_020_REF_IMPL_SEND_EXT_KEYS_BASE_URL         | The `ext_keys` endpoint to send requests to.|
| ETSI_020_REF_IMPL_SEND_EXT_KEYS_ACK_CALLBACK_URL | The ack callback url to use when sending `ext_keys` requests.|
| ETSI_020_REF_IMPL_SEND_EXT_KEYS_KEY_COUNT        | The quantity of keys to send.|
| ETSI_020_REF_IMPL_SEND_EXT_KEYS_KEY_SIZE_BITS    | The size of each key in bits.|
| ETSI_020_REF_IMPL_INTRA_NETWORK_SAE_IDS          | Which SAE IDs originate from within our network.|
| ETSI_020_REF_IMPL_THIRD_PARTY_SAE_IDS            | Which SAE IDs can be relayed by this key gateway.|

Refer to [.env](.env) file for more details.

# Examples

The `examples` folder contains multiple bash scripts that show the user how to
launch and interact with the reference implementation.
Each of the scripts sends requests to the `ext_keys` endpoint of the server.
The `call_invalid_ext_keys.sh` script sends some exemplary invalid requests.

The Makefile allows the user to run these scripts in a coordinated way.

First, run server A:
```bash
make run_server_a
```

Next, run server B in tandem:
```bash
make run_server_b
```

Finally, run any one of the example scripts via their targets:

* `make run_ext_keys`
* `make run_ext_keys_multiple_keys`
* `make run_ext_keys_multiple_sae_ids`
* `make run_ext_keys_multiple_keys_and_sae_ids`
